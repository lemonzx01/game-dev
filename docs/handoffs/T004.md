## Design
- Vitals follow ARCHITECTURE §4 "derived from elapsed time and updated at thresholds": each entity stores an anchor `(tick, hunger, thirst, health)` in fixed-point milli-units (0..1,000,000). Current values are computed from elapsed ticks (`VitalsAnchor.At`), with no per-tick update per entity.
- Health regenerates while both needs are below max; each maxed need applies its damage rate (starvation / dehydration). The death tick is solved analytically from at most three constant-rate segments and booked once as **required** scheduler work (priority 0), so it runs before discretionary AI on that tick.
- Eating/drinking (`TryConsume`, internal; T005 actions will call it) re-anchors and re-books death. The superseded booking stays in the queue and is ignored when due (`ScheduledDeathTick` check).
- Death at tick D: actions cleared, `LifeState = Dead`, one `EntityDied` event (Target = id, Reason = cause) and a durable `DeathRecord` written together. The snapshot for D shows the row as Dead; the row is removed at the start of D+1. `ReadEntityDetails` keeps returning identity, birth, final needs, death tick and cause from the record. `ReadHistory` pages death milestones by EventSequence (ARCHITECTURE §3 cursor rules).
- Death events are "critical": never dropped by the per-tick cap (they still count toward it). `Emit` now returns the assigned EventSequence.
- Defaults are provisional balance values (`VitalsConfig.Default`): hunger maxes in ~3 days, thirst in ~1.5 days, then death in ~1 day / ~0.5 day.
